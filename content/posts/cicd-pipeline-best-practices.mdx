Modern software teams ship faster than ever, but speed without safeguards is just chaos in a trench coat. This post walks through the pipeline patterns I've adopted to keep code quality high and releases boring (the good kind of boring).

## The Pipeline Philosophy

Every pipeline should answer three questions before a deploy:

1. **Does it build?** — TypeScript compiles, dependencies resolve, no import tragedies.
2. **Does it pass the gates?** — Linting, formatting, and type-checking all agree.
3. **Does it deploy safely?** — Preview deploys, rolling updates, quick rollbacks.

## Linting as a Pre-commit Ritual

Husky + lint-staged catches sloppy code before it ever hits the remote:

```json
{
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": "eslint --fix"
  }
}
```

Combine this with a CI check that runs the same linter, and you've got a safety net that catches drift between local and CI environments.

## Matrix Testing

When you need to test across Node versions or OS targets, GitHub's matrix strategy shines:

```yaml
strategy:
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest, macos-latest]
```

This multiplies your safety coverage without writing duplicate workflow files.

## What I Learned the Hard Way

- Env vars that differ between CI and local can waste hours. Centralize them.
- Caching `node_modules` properly cuts build times by 60–70%.
- Always test your rollback path — not just your deploy path.

Ship fast. Ship safe. Let the machines do the remembering.
